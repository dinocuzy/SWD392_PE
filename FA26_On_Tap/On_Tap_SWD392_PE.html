01. Hướng dẫn vẽ Class Diagram (Xuất hiện 10/10 đề - 2.5 đến 4.0 điểm)

File mẫu mở trong Draw.io Desktop: 01_Template_Class_Diagram_PE.drawio

Quy tắc 5 bước ăn trọn điểm Class Diagram

  1. Mỗi Class phải chia đúng 3 ngăn: Tên Class, ngăn Attributes có dấu - (private) kèm kiểu dữ liệu (String, Double, DateTime, Boolean), và ngăn Methods có dấu + (public) kèm kiểu trả về.
  2. Nếu 2 lớp có chung tập thuộc tính (như Passenger và Driver cùng có id, fullName, phone), tạo lớp cha User và nối mũi tên Inheritance (nét liền + tam giác rỗng) trỏ lên User.
  3. Phân biệt rõ Composition (thoi đặc) cho các phần tử phụ thuộc sống còn (Order *-- OrderItem, MedicalRecord *-- Prescription) và Aggregation (thoi rỗng) cho các phần tử độc lập (Department o-- Doctor, Course o-- Lesson).
  4. Kiểm tra 100% các đường nối phải có con số Multiplicity (1, 0..1, 0..*, 1..*) ở cả 2 đầu dây.

02. Hướng dẫn vẽ Sequence Diagram (Xuất hiện 9/10 đề - 2.5 đến 4.0 điểm)

File mẫu mở trong Draw.io Desktop: 02_Template_Sequence_Diagram_PE.drawio

Các điểm bắt buộc phải có

  • Sắp xếp đúng thứ tự Lifeline từ trái sang phải: Actor > UI/View > Controller > Service > Repository / External Gateway > Database.
  • Đánh số thứ tự phân cấp cho mọi lời gọi: 1, 1.1, 1.1.1, 1.1.2.
  • Bắt buộc có khung alt [điều kiện thành công] / [else: điều kiện thất bại] và mũi tên trả về dùng nét đứt.

05. Khung 4 Design Pattern xuất hiện trong đề thi

File mẫu mở trong Draw.io Desktop: 07_Template_4_Design_Patterns_PE.drawio

1. Strategy Pattern (Đổi thuật toán / Thanh toán)

[Context: PaymentService]
  - strategy: IPaymentStrategy
  + setStrategy(s: IPaymentStrategy): void
  + executePayment(amount: Double): Boolean
        | o---> <<interface>> [IPaymentStrategy]
                      + pay(amount: Double): Boolean
                             ^ (Nét đứt + tam giác rỗng)
               +-------------+-------------+
       [CreditCardStrategy]         [EWalletStrategy]

2. Observer Pattern (Thông báo đa kênh)

[Subject: OrderNotifier]
  - observers: List<IObserver>
  + attach(o: IObserver): void
  + notifyAll(msg: String): void
        | o---> <<interface>> [IObserver]
                      + update(msg: String): void
                             ^ (Nét đứt + tam giác rỗng)
               +-------------+-------------+
         [EmailNotifier]             [SMSNotifier]

3. Singleton Pattern (1 Instance quản lý duy nhất)

[OrderManager]
-----------------------------------------
- static instance: OrderManager
- configData: Map<String, String>
-----------------------------------------
- OrderManager()   <-- Constructor PRIVATE (-)
+ static getInstance(): OrderManager

4. Factory Method Pattern (Khởi tạo theo loại)

[BouquetFactory]
  + createBouquet(type: String): IBouquet
        | (Dependency nét đứt)
        v
<<interface>> [IBouquet]
  + getPrice(): Double
        ^ (Nét đứt + tam giác rỗng)
  +-----+------------------+
[WeddingBouquet]    [BirthdayBouquet]

06. Khung trả lời 4 dạng câu hỏi viết trong đề

A. Functional vs Non-Functional Requirements (Đề SU25 Cinema - 1.0đ)

Functional Requirements: (1) Allow users to search, filter, and view details of items/schedules; (2) Allow users to create bookings/orders with real-time validation; (3) Process payments via integrated gateways and issue receipts; (4) Allow administrators to manage catalog, schedules, and reports.

Non-Functional Requirements (Luôn kèm con số đo lường): (1) Performance: 95% of API responses within 2.0 seconds; (2) Concurrency: Support 5,000 concurrent users with locking to prevent double-booking; (3) Availability: 99.9% uptime with daily backups; (4) Security: Passwords hashed with bcrypt, traffic encrypted via TLS 1.3, RBAC enforced.

B. Đề xuất System Architecture (Đề Flower Shop & CyberAIFPTx - 2.0đ)

Trình bày mô hình 4-Tier Layered Architecture: (1) Presentation Layer (Web/Mobile UI), (2) API Gateway / Controller Layer (Routing, JWT Auth, DTO validation), (3) Business Service Layer (Core services áp dụng Strategy/Observer/Factory), (4) Data Access & Persistence Layer (Repository + Relational DB + Redis Cache). Lý do chọn: Separation of Concerns, High Maintainability, Independent Scalability.

C. Bảng Use Case Specification (Đề SP26/FA26 Food Delivery - 2.5đ)

Gồm đủ 6 dòng: Use Case Name, Primary Actor, Preconditions (User logged in, valid items selected), Postconditions (Order saved as CONFIRMED, payment recorded), Main Success Scenario (6 bước đánh số 1-6 tương tác giữa Actor và System), Alternative/Exception Flows (2a. Out of stock, 5a. Payment declined).

D. Chuyển Class Diagram sang Database Schema (Đề Fall25 E-Learning - 1.0đ)

Quan hệ 1 - N: Đặt khóa ngoại FK ở bảng phía Nhiều (*). Quan hệ N - N: Tách thành bảng trung gian chứa 2 khóa ngoại FK trỏ về 2 bảng chính. Quan hệ 1 - 1: Đặt FK UNIQUE ở bảng phụ thuộc.

TỰ KIỂM TRA PHẢN XẠ TRƯỚC GIỜ THI

01. Class A thực thi (implement) Interface B thì vẽ mũi tên gì?
Dùng quan hệ Realization: Đường NÉT ĐỨT + đầu TAM GIÁC RỖNG trỏ về phía <<interface>> B.
02. Giữa MedicalRecord và Prescription dùng hình thoi đặc hay rỗng? Đặt ở đâu?
Dùng Hình thoi ĐẶC (Composition) đặt sát cạnh MedicalRecord (phía Whole), vì xóa bệnh án thì đơn thuốc bên trong không tồn tại độc lập.
03. Chiều mũi tên <<include>> và <<extend>> trong Use Case khác nhau thế nào?
<<include>>: Mũi tên nét đứt trỏ từ UC Chính sang UC Phụ bắt buộc.
<<extend>>: Mũi tên nét đứt trỏ từ UC Phụ tùy chọn ngược về UC Chính.
04. Đề bài yêu cầu vẽ "Conceptual ERD (Chen's Notation)", có được ghi FK và kiểu dữ liệu không?
Tuyệt đối KHÔNG. Chen's ERD chỉ dùng Hình chữ nhật (Entity), Hình thoi (Relationship), Hình Elip (Attribute) và gạch chân khóa chính trong Elip.
